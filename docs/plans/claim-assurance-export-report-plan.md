# Plan: Claim Assurance Export Reports

**Status: JSON/Markdown API, CLI, UI export links, saved report jobs,
downloads, and report retention implemented**

## Goal

Provide a comprehensive, durable snapshot of Claim Assurance data that can be
saved outside Observatory and handed to asynchronous agents or humans working on
upstream project improvements.

The export should answer:

- what claims were extracted;
- where each claim came from;
- how each claim was verified;
- what evidence supported the verdict;
- which contradicted or insufficient-evidence claims were explained;
- what remediation target each explanation identified; and
- how canonical claim groups affect interpretation without hiding occurrence
  provenance.

The output may be Markdown, JSON, or both. JSON is the source of record for
agent consumption; Markdown is the review-friendly projection.

## Implementation Status

The implementation provides export paths for bounded snapshots:

- `GET /api/v2/claims/reports/export.json` returns a self-contained structured
  snapshot with filters, summary counts, occurrences, extraction evaluation,
  verification history, evidence, explanation history, human overrides,
  canonical groups, aggregates, and warnings.
- `GET /api/v2/claims/reports/export.md` renders the same report object as a
  deterministic Markdown review artifact.
- `scripts/export-claim-assurance-report.py` writes JSON, Markdown, or both from
  a running Observatory API and requires an explicit scope filter or `--all`.
- The Claim Triage occurrence tab exposes `Export JSON` and `Export Markdown`
  links using the supported active filters: claim type, verdict, Jira key,
  source file, and numeric occurrence search.
- `POST /api/v2/claims/reports` creates a saved report job. The current job
  implementation generates the bounded snapshot immediately, persists requested
  JSON and/or Markdown artifacts, and returns durable metadata.
- `GET /api/v2/claims/reports/{report_id}` returns saved job metadata.
- `GET /api/v2/claims/reports/{report_id}/download?format=json|markdown`
  downloads a persisted artifact.
- Report jobs expire through retention cleanup after the configured retention
  window.

The API uses an explicit limit and emits warnings when matching rows exceed the
exported row count. Fully detached background execution is not required for the
current local workflow; the persisted job contract keeps that upgrade path open.

## Problem

Observatory can show claim, verification, explanation, and consolidation state
through APIs and UI pages, but that state is difficult to package for offline or
asynchronous use. Agents improving related projects need a stable bundle they
can read without querying Observatory repeatedly or losing context about source
files, evidence, verdict history, and improvement routing.

Current gaps:

1. There is no one-command export for a claim-assurance snapshot.
2. API consumers must reconstruct relationships across occurrences,
   verification runs, explanation runs, evidence rows, human overrides, and
   canonical groups.
3. Markdown summaries are useful for humans, while separate agents need
   structured JSON with stable identifiers and provenance.
4. The export needs clear scoping so teams can generate snapshots by Jira key,
   artifact type, verdict, source file, canonical group, or date range.

## Non-Goals

- Do not make exported reports editable state that can be re-imported as truth.
- Do not replace the immutable Observatory database as the system of record.
- Do not authorize automatic claim consolidation or verification reuse from an
  export alone.
- Do not include secrets, raw credentials, or unrestricted job logs.
- Do not collapse occurrences into canonical groups in a way that loses source
  provenance.

## Proposed User Experience

Add an export capability available through both API and CLI:

```bash
scripts/export-claim-assurance-report.py \
  --api-base-url http://observatory.local \
  --jira-key RHAIRFE-1 \
  --format both \
  --output var/reports/rhairfe-1-claim-assurance
```

Expected outputs:

```text
var/reports/rhairfe-1-claim-assurance.json
var/reports/rhairfe-1-claim-assurance.md
```

The UI can later expose the same export as a button on the Claim Triage page.
The initial implementation should prioritize the API and CLI path so snapshots
can be generated by automation.

## Scope and Filters

Support filters aligned with existing triage workflows:

- `jira_key`
- `claim_occurrence_id`
- `normalized_claim_id`
- `canonical_group_id`
- `artifact_type`
- `pipeline_slug`
- `source_file`
- `claim_type`
- `verdict`
- `processing_state`
- `explanation_category`
- `improvement_target`
- `human_review_required`
- `created_after` / `created_before`

The export should record the exact filters used and the export timestamp. If no
filter is supplied, require an explicit `--all` flag in the CLI to avoid
accidentally generating very large reports.

## Data Included

Each export should include:

### Export metadata

- export schema version;
- generated timestamp;
- Observatory base URL;
- filters;
- row counts;
- API/server version if available; and
- warnings for truncated or unavailable sections.

### Claim occurrences

- occurrence ID;
- normalized claim ID;
- canonical group ID and canonical text when present;
- claim text, original text, claim type, modality, product version, temporal
  scope;
- source file, source locator, source unit text when available;
- Jira keys;
- extraction run metadata and extraction-assurance outcomes.

### Verification history

- all verification runs for each occurrence, not only the effective verdict;
- effective verification run ID;
- verdict, severity, confidence, verifier revision, model, harness,
  repository revision, configuration digest, evidence context digest;
- evidence summary; and
- structured evidence records.

### Explanation history

- all explanation runs attached to each verification run;
- effective explanation run ID;
- category, improvement target, human-review flag;
- explanation, contributing factors, alternatives, remediation, regression test;
- structured explanation evidence; and
- regression runs.

### Human overrides

- override decision;
- actor;
- rationale;
- target verification run; and
- timestamp.

### Canonical groups

- group ID and canonical text;
- active and retired memberships relevant to exported occurrences;
- equivalence decisions when available;
- qualifier summary; and
- retirement state.

### Aggregates

- counts by verdict, claim type, artifact type, source file, Jira key,
  explanation category, improvement target, and canonical group;
- contradicted and insufficient-evidence hotspots;
- repeated/canonicalized claims; and
- claims requiring human review.

## JSON Shape

The JSON export should be deterministic and self-contained:

```json
{
  "schema_version": "claim-assurance-report.v1",
  "generated_at": "2026-07-17T12:00:00Z",
  "filters": {"jira_key": "RHAIRFE-1"},
  "summary": {"occurrences": 42, "contradicted": 3},
  "occurrences": [{
    "id": 123,
    "normalized_claim_id": 45,
    "canonical_group": {"id": 7, "canonical_text": "..."},
    "claim_text": "...",
    "source": {"file": "...", "locator": "..."},
    "effective_verification_run_id": 456,
    "verification_runs": [],
    "human_overrides": []
  }],
  "canonical_groups": [],
  "aggregates": {},
  "warnings": []
}
```

Use stable keys and arrays. Do not require consumers to infer relationships from
human-readable Markdown.

## Markdown Shape

Markdown should be optimized for async review:

1. Title, filters, timestamp, and counts.
2. Executive summary of contradicted, insufficient-evidence, and human-review
   items.
3. Hotspots grouped by Jira key, source file, improvement target, and canonical
   group.
4. Detailed occurrence sections with claim text, source, effective verdict,
   evidence summary, explanation, remediation, and links/IDs for history.
5. Appendix containing full verification and explanation histories.

Markdown may omit bulky raw evidence fields when the JSON export is generated
alongside it, but it must reference the corresponding JSON IDs.

## API Design

Add read-only endpoints:

```text
GET /api/v2/claims/reports/export.json
GET /api/v2/claims/reports/export.md
```

Both endpoints accept the same filters. The JSON endpoint returns structured
data. The Markdown endpoint renders the same data through a deterministic
server-side projection.

For saved exports, use the report job endpoints:

```text
POST /api/v2/claims/reports
GET  /api/v2/claims/reports/{report_id}
GET  /api/v2/claims/reports/{report_id}/download
```

The first implementation executes the job immediately with explicit limits and
clear truncation warnings while preserving the same durable job/download
contract expected by later background workers.

## CLI Design

Add `scripts/export-claim-assurance-report.py` as a thin API client. It should:

- require `--api-base-url` or use `OBSERVATORY_URL`;
- require at least one scope filter or `--all`;
- support `--format json|markdown|both`;
- write atomically to the requested output path;
- fail on non-2xx API responses;
- print counts and output paths; and
- avoid embedding local-only absolute paths unless they came from Observatory
  provenance fields.

## Implementation Phases

### Phase 1: Structured export service

- Add backend query helpers that assemble occurrence histories in bulk.
- Reuse existing history/triage projections where possible.
- Add JSON export endpoint with filters and row-count summary.
- Add tests against a real SQLite database covering claims, verification runs,
  explanations, evidence, overrides, and canonical groups.

### Phase 2: Markdown projection and CLI

- Add deterministic Markdown renderer over the JSON export object.
- Add Markdown endpoint.
- Add CLI wrapper for JSON, Markdown, and combined export.
- Add snapshot-style tests for small representative exports.

### Phase 3: UI affordance

- Add an export button to the Claim Triage page.
- Carry current table filters into the export request.
- Show warnings when the export would exceed synchronous limits.

### Phase 4: Large export jobs

- Persist report job metadata and generated artifacts.
- Add immediate persisted generation for bounded snapshots.
- Add retention policy for generated report artifacts.
- Defer detached background workers until all-project or all-time snapshots need
  longer execution than the request path can safely support.

## Testing Requirements

- Backend endpoint tests must use real SQLite fixtures.
- JSON export tests must assert stable IDs and full relationship coverage.
- Markdown tests must assert the main sections and important remediation fields.
- CLI tests should mock only HTTP transport, not export shaping logic.
- Include at least one canonical group fixture to verify that grouping is shown
  without losing occurrence-level provenance.

## Risks and Constraints

- Large exports may be expensive. The synchronous endpoint should enforce a
  configurable maximum and return a clear overflow error.
- Reports can contain sensitive source text. Access control must match or exceed
  the existing Claim Assurance read permissions before exposing this outside the
  local deployment.
- Markdown is lossy. JSON must remain the source of record for agent workflows.
- Exports are snapshots. Consumers must not assume they represent current
  Observatory state after generation time.

## Open Questions

- Should the first UI export download one file or a `.tar.gz` bundle containing
  both JSON and Markdown?
- Should the CLI grow a `--saved-job` mode that creates a persisted report job
  before downloading artifacts, or is direct synchronous export enough for local
  automation?
- What maximum occurrence count is acceptable for synchronous export in the
  deployed environment?
